## 1. Назначение проекта

**DocGen Portable** — автономное (без обязательного бэкенда и интернета) веб-приложение для кадровика/специалиста по охране трудаsmall предприятия. Решает задачи:

- формирование комплекта документов по охране труда: вводный инструктаж, листы стажировки, листы ознакомления с ЛНА/инструкциями, направления на медосмотр (МО) и психиатрическое освидетельствование (ПСО);
- ведение контингента работников для медосмотров по Приказу МЗ РФ № 29н и списков ПСО по Приказу № 342н (в контексте СОУТ — 426-ФЗ);
- импорт/экспорт данных через Excel и генерация готовых `.docx` по шаблонам прямо в браузере.

**Способ использования:** распаковка папки на ПК/флешку → запуск `start.bat` (Windows 10/11, без установки Node.js — используется PowerShell или `server.cjs`; либо `npm run dev` через Express-сервер `server.ts`) → работа в браузере на `http://localhost:3000`.

**Подтверждено реализацией:** всё перечисленное выше работает в коде (см. разделы 3–4).
**Является планом (НЕ реализовано):** предпросмотр шаблонов + редактор Tiptap (этап B), адаптивность интерфейса (этап A), единый `constants.ts` (этап E), загрузка PDF-сканов карт СОУТ.

## 3. Текущее состояние проекта

### Реализовано (подтверждено кодом)
- **Единая модель данных** (`src/lib/types.ts`): Employee, JobDirectoryItem, SoutWorkplace, HarmFactorConfig, Company; устаревшие поля Employee (`factors29n`, `pso342n`, `periodicity`, `soutClass`, `soutCardNumber`) помечены `@deprecated`.
- **Множественность компаний с изоляцией по companyId** (модель A): переключатель `CompanySelector`, модалка `CompanyModal`, пошаговый мастер `CompanySetupWizard` (штатное расписание → поимённый список → остальное).
- **Контингент как материнская модель**: класс СОУТ, вредные факторы (`factorsConfig` с периодичностью) и психиатрия (`psychiatryPoints`) читаются всеми вкладками только из справочника должностей; в карточке сотрудника класс СОУТ read-only.
- **Вкладки приложения** (10): Инструктажи, Направления, График медосмотров, Сотрудники, Контингент, СОУТ, Excel, Шаблоны, Компания, История/Резервные копии.
- **Демо-данные ООО «Катания»** (`defaultData.ts`, объём проверен grep’ом): 25 должностей + 9 сотрудников + 25 карт СОУТ = 59 записей с `companyId`; `soutClass` встречается 50 раз; `factorsConfig` заполнен у 10 должностей; класс 3.1 — 9 должностей + 10 мест СОУТ.
- **Генерация DOCX в браузере** (`docxEngine.ts`, ~750 строк): шаблоны с тегами `{{...}}`, расчёт «эффективного класса СОУТ» только из jobDirectory, расчёт дат через производственный календарь (`holidays.ts`: следующий рабочий день, формат DD.MM.YYYY).
- **Excel-перенос** (`excelParser.ts` + `ExcelTransferView`): импорт сотрудников/должностей с автоматическим проставлением активного `companyId`, экспорт, шаблон-заготовка, график медосмотров; нормализация пола `normalizeGender()`.
- **Массивная вставка из Excel** (`BatchPasteModal`, Ctrl+V) с проставлением `companyId`.
- **Portable-режим** (`portableManager.ts`): экспорт/импорт проекта в JSON, ZIP-бандл дистрибутива; запись файлов в локальные папки через API сервера (если сервер запущен) либо сохранение через браузер.
- **Service Worker** (`public/sw.js`) и `manifest.json` — офлайн-кэширование статики; установка как PWA («DesktopModeModal»).

## 4. Основные пользовательские сценарии (подтверждены кодом)

1. **Приём сотрудника:** EmployeesView (или BatchPasteModal/Excel) → выбор должности из контингента → InstructionsView отмечает флаги генерации → генерация Вводный/СЛ/Лист_ИТР|Рабочие|Офис/МО/ПСО → скачивание DOCX (или ZIP), опциональная запись в папки `инструктажи\`, `Направления\` через серверный API.
2. **Периодические медосмотры (29н):** MedicalScheduleView формирует список по `factorsConfig` должностей (периодичность 1 год / 2 года + `harmFactorsCompletedLastYear`) → DirectionsView генерирует направления МО в `готовые_направления\`.
3. **Психиатрия (342н):** контур формируется только для должностей с `psychiatryPoints` (например, пункт 11); ПСО — при предварительном медосмотре.
4. **Новая компания:** CompanySelector → CompanySetupWizard: шаг 1 — штатное расписание (должности+подразделения), шаг 2 — поимённый список, шаг 3 — остальные данные; все вкладки фильтруются по активной компании.
5. **Резервное копирование:** HistoryAndBackupView → экспорт JSON / импорт JSON / ZIP-дистрибутив.

Непроверенное вручную: пункты 1–5 протестированы только статически (tsc/build проходят); браузерная проверка — за куратором.

## 5. Данные и их сохранность

- **Категории данных:** персональные данные работников (ФИО, даты рождения/приёма, СНИЛС, телефон, пол), сведения о должностях, СОУТ (классы, факторы, номера карт), реквизиты организации, шаблоны .docx, история действий. Всё хранится локально, на сервер не передаётся (Gemini API в коде не вызывается).
- **Хранение:** localStorage браузера, ключ `docgen_portable_state_v1` + суффиксы `_emp`, `_jobs`, `_sout`, `_comp`, `_companies`, `_active_comp_id`, `_hist`. Данные переживают перезапуск браузера.
- **Резервирование:** экспорт/импорт всего состояния в JSON; ZIP-бандл portable-дистрибутива; повторное открытие того же браузера/профиля восстанавливает данные.
- **Ограничения:** привязка к профилю браузера (перенос только через JSON/ZIP); риск переполнения квоты localStorage; очистка данных сайта = потеря всей базы без предупреждения; при работе через `file://` (без сервера) часть функций записи в ФС недоступна — сохраняется только браузерная загрузка файлов.

## 6. Критические ограничения проекта

Подтверждённые архитектурные правила (нарушение ломает консистентность данных):
1. **Не менять схему JSON/localStorage без явного согласования** — старые снимки пользователей должны оставаться читаемыми (legacy-поля оставлены в типах именно для этого).
2. **Класс СОУТ берётся ТОЛЬКО из JobDirectoryItem/SoutWorkplace.** Переопределение в Employee запрещено (`docxEngine`: `effectiveSoutClass = job?.soutClass || '2'`).
3. **Периодичность факторов живёт только в `HarmFactorConfig.periodicity`**, не в Employee.
4. **Каждая новая запись Employee/JobDirectory/Sout обязана получать активный `companyId`** — иначе нарушается изоляция компаний (списки «СибТрансСервиса» должны быть пусты).
5. **gender строго `'м' | 'ж'`**; в UI отображать «Мужской/Женский»; при импорте нормализовать через `normalizeGender()`.
6. **Формат дат — DD.MM.YYYY**; рабочие дни считать через `holidays.ts`.
7. После любых правок `docxEngine.ts`/шаблонов — **проверять генерацию DOCX** хотя бы на демо-данных Катании.
8. Сохранять переносимость: не вводить обязательный сетевой доступ, не ломать `base: './'` и работу без npm (server.cjs/start.bat).
9. Не удалять функции/данные и не переписывать модули целиком без разрешения (рекомендация владельца проекта, зафиксирована как правило работы).
