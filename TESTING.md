## 1. Назначение и область

Документ описывает, **как** проверять DocGen Portable после изменений: что можно проверить автоматически, что требует ручного прогона в браузере, и какие известные ограничения (R1–R15 из TASK_STATUS.md) нужно учитывать при интерпретации результатов.

**В проекте отсутствует (это ограничение текущего состояния, а не задача этапа):**
- автоматические тесты (unit/integration/e2e) — нет ни одного тестового файла и тест-раннера (TASK_STATUS.md, R1);
- CI — конфигурационных файлов сборочных систем в репозитории нет;
- отдельный линтер — npm-скрипт `lint` = `tsc --noEmit`, только проверка типов;
- e2e-проверки генерации DOCX/XLSX — только вручную в Word/LibreOffice/Excel.

Следовательно, **регрессии ловятся исключительно вручную**. Успешные `lint` и `build` доказывают только компилируемость кода, но не работоспособность функций (см. PROJECT_CONTEXT.md, ограничение №8).

Связанные документы: `PROJECT_CONTEXT.md`, `ARCHITECTURE.md`, `TASK_STATUS.md`.

## 2. Быстрые проверки (автоматизируемые)

Команды взяты из `package.json` (devDependencies: vite ^8.3.0, typescript ^7.0.2, tsx; скрипты — фактические).

| Команда | Что проверяет | Успех | Провал |
|---|---|---|---|
| `npm run lint` | Типы (`tsc --noEmit`) | exit 0, пустой вывод | список ошибок TS; правки, их вызвавшие, откатывать или чинить до дальнейших проверок |
| `npm run build` | Прод-сборка Vite в `dist/` | сообщение «built in …», файлы в `dist/` | ошибки сборки; предупреждение «chunk larger than 500 kB» — НЕ провал, это известный риск R9 |
| `npm run dev` | Dev-сервер (`tsx server.ts`, порт 3000) | сервер слушает :3000, открывается приложение | падение при старте, ошибка порта; сам факт старта не доказывает работу функций |
| `npm run preview` | Раздача собранной `dist/` (`vite preview`) | приложение открывается по адресу из вывода | белый экран / 404 — проблема base-путей или сборки |
| `npm start` | `node server.ts` | — | **Работоспособность не подтверждена (R13):** `server.ts` — TS-модуль с ESM-импортами, запуск прямым `node` без транспиляции ожидаемо не работает; проверять на практике отдельно. Успешный старт не доказывает работу приложения |

Порядок быстрой проверки после любых правок: `npm run lint` → `npm run build` → ручной прогон затронутых сценариев из §4.

## 3. Среда и предусловия ручных проверок

- **Браузер:** предпочтителен актуальный Chromium (Chrome/Edge) — генерация DOCX/XLSX идёт через Blob-скачивание, Service Worker и `docxtemplater/pizzip/jszip/exceljs` в браузере.
- **Режимы запуска (все четыре ведут себя по-разному — фиксировать режим в отчёте!):**
  1. dev: `npm run dev` → http://localhost:3000;
  2. preview: `npm run build && npm run preview` (раздача `dist/`);
  3. file:// из папки `app/` через `start.bat` (Windows);
  4. прод-сервер `server.cjs` (нужен для полного ZIP-бандла, см. §4 «ZIP»).
- **Демо-данные:** ООО «Катания» (`comp-catania`: 25 должностей, 9 сотрудников, 25 карт СОУТ) и ООО «СибТрансСервис» (`comp-sibtrans`: заведомо пустая — пустые списки в ней являются нормой и служат базой проверки изоляции).
- **Перед прогоном:** очистить или зафиксировать localStorage-ключи `docgen_portable_state_v1_*`. Помнить: **templates (файлы .docx) и holidaysList не персистятся** и сбрасываются после F5 (R3) — это текущее ожидаемое поведение, а не новый баг.

## 4. Ручные сценарии по функциональным блокам

Формат: цель → шаги → ожидаемый результат → что фиксировать при провале.

### 4.1 Сотрудники (EmployeesView)
- **Цель:** CRUD + изоляция + batch-paste.
- **Шаги:** добавить сотрудника (ФИО, пол «Мужской/Женский», должность из справочника); отредактировать; удалить; переключить компанию; выделить строки и нажать Ctrl+V с табличным текстом из буфера.
- **Ожидание:** у нового сотрудника проставлен `companyId` активной компании (подтверждено кодом: EmployeesView.tsx:188, :222); в СибТрансСервисе список пуст; класс СОУТ в карточке read-only (берётся из должности); batch-paste создаёт записи тоже с `companyId`.
- **При провале:** JSON-бэкап на момент ошибки + скриншот консоли.

### 4.2 Контингент / справочник должностей (ContingentView)
- **Цель:** редактирование `factorsConfig` и `psychiatryPoints` (источник истины).
- **Шаги:** открыть контингент Катании, изменить периодичность фактора у job-12, добавить/убрать пункт «11» психиатрии, сохранить; перезагрузить страницу.
- **Ожидание:** изменения сохраняются в localStorage и видны во всех вкладках-потребителях (медосмотры, график, направления). **Внимание (R7): ContingentView не получает `activeCompanyId`** — при переключении на СибТрансСервис может показывать должности Катании; это известное состояние, фиксировать как подтверждение R7, а не как новый дефект.

### 4.3 СОУТ (SoutView)
- **Шаги:** добавить карту; переключить компанию.
- **Ожидание:** строгая фильтрация `(w.companyId || '') !== activeCompanyId → скрыто` (SoutView.tsx:88) — в СибТрансСервисе 0 карт, у Катании 25.

### 4.4 Инструктажи (InstructionsView)
- **Шаги:** выбрать сотрудников, отметить `needGeneration`, запустить генерацию, скачать DOCX.
- **Ожидание:** изоляция по легаси-правилу (InstructionsView.tsx:93–102); в сгенерированных DOCX — корректные ФИО/должность/даты DD.MM.YYYY. **Открытый вопрос Q1:** правило «ПСО только при предварительном МО» здесь НЕ действует (docxEngine.ts:603 добавляет ПСО без проверки типа) — зафиксировать фактическое поведение как ответ на Q1, багом не считать.

### 4.5 Направления МО/ПСО (DirectionsView)
- **Шаги:** сформировать направление на медосмотр для сотрудника с вредными факторами; отдельно — на ПСО.
- **Ожидание:** в directions ограничение «ПСО только при предварительном МО» действует (docxEngine.ts:711–716) — проверить оба случая (R11). **R7:** DirectionsView пропс `activeCompanyId` не получает; работает со списком переданных сотрудников — зафиксировать, смешиваются ли компании в выборке.

### 4.6 График медосмотров (MedicalScheduleView)
- **Шаги:** выбрать `examTypeMode`, проверить eligibility по классу СОУТ/факторам должности, запланировать, экспортировать XLSX.
- **Ожидание:** eligibility считается из `job.soutClass` и `job.factorsConfig`; XLSX открывается в Excel. **R7:** пропс `activeCompanyId` не передаётся — зафиксировать поведение при переключении компаний.

### 4.7 Шаблоны (TemplatesView)
- **Шаги:** загрузить пользовательский .docx, сгенерировать документ по нему, скачать эталонный шаблон, сделать F5.
- **Ожидание:** после перезагрузки пользовательские шаблоны сброшены к встроенным — **текущее ожидаемое поведение (R3)**, а не новый баг; зафиксировать факт.

### 4.8 Excel (ExcelTransferView)
- **Шаги:** импорт файла с листами «СПИСОК» и «ДАННЫЕ» (в т.ч. пол «м/ж/муж/жен»), посмотреть предупреждения; экспорт базы сотрудников, базы должностей, графика, пустого бланка.
- **Ожидание:** при импорте всем Employee и JobDirectory присваивается активный `companyId` (ExcelTransferView.tsx:73–74); `normalizeGender()` приводит «муж»→'м'; экспортированные файлы открываются.

### 4.9 Компании и мастер создания (CompanySelector / CompanySetupWizard)
- **Шаги:** создать новую компанию через мастер: шаг 1 штатное расписание (должности+подразделения) → шаг 2 поимённый список → шаг 3 карты СОУТ.
- **Ожидание:** все созданные записи имеют `companyId` новой компании (App.handleCompanySetupComplete, App.tsx:350–357); во всех вкладках новая компания сначала пустая или содержит ровно внесённое.

### 4.10 Изоляция companyId (сквозной)
- **Шаги:** переключить Катания ↔ СибТрансСервис последительно во всех вкладках; вернуться на Катанию.
- **Ожидание:** Employees/Instructions/Sout — чисто; Contingent/Directions/MedicalSchedule — **зафиксировать фактическое смешение (R7)** как известное состояние. Данные Катании после возврата complete — на месте.

### 4.11 JSON-бэкап (HistoryAndBackupView)
- **Шаги:** экспорт JSON → очистить localStorage → импорт.
- **Ожидание:** восстанавливаются employees, jobDirectory, history, companies, activeCompanyId (состав ProjectBundle, portableManager.ts:6–16). **soutWorkplaces и templates в бэкап не входят (R4/R5)** — после импорта карты СОУТ и загруженные шаблоны отсутствуют: текущее ожидаемое поведение, зафиксировать объём потери.

### 4.12 ZIP-дистрибутив (portableManager)
- **Шаги:** собрать бандл из HistoryAndBackupView в dev-режиме и при запущенном прод-сервере (`server.cjs`); распаковать.
- **Ожидание:** состав — start.bat/run.ps1/stop.bat/инструкция/шаблоны/эталонный XLSX/`data/project_backup.json`/файлы приложения. В dev-режиме бандл неполный (без вложения app/) — R6. Вложенный `project_backup.json` формируется с пустыми history/companies (portableManager.ts:345) и **неполнее** пользовательского экспорта — R6, зафиксировать сравнением двух JSON.

### 4.13 Генерация DOCX (сквозной)
- **Шаги:** для каждого типа (инструктажи, направления МО, направления ПСО) сгенерировать и открыть файл в Word/LibreOffice.
- **Ожидание:** подстановки tag-полей корректны, даты DD.MM.YYYY, ФИО/должность/класс СОУТ соответствуют данным контингента. Открыть именно в редакторе — tsc/build это не проверяют.

### 4.14 Windows-запуск (start.bat / run.ps1 / stop.bat)
- Требует реальной Windows-машины. **В текущей среде непроверяемо (R13)** — помечать как «непроверено», а не как «работает».

## 6. Что приносить в отчёте о провале

1. Номер сценария (§4.x) и конкретный шаг.
2. Ожидаемое vs фактическое поведение.
3. Скриншот или текст ошибок консоли браузера (F12).
4. Данные воспроизведения — по возможности JSON-бэкап на момент ошибки (без ПДн, если отчёт внешний).
5. Режим сборки: dev / preview / app-file:// / server.cjs — обязательно указать.
